# GSB Bugfix Task
## 题面
终端杀毒的文件访问拦截最近误放行了一批勒索样本，复盘发现内核文件通知队列一满，裁决服务就把后续访问全放过去了。安全运营调出当天的队列指标，发现溢出前后没有任何告警，只有一条被冲掉的计数；终端用户看到的是文件正常打开，根本不知道扫描被跳过了。分发器在队列溢出后默认放行；事件里的文件描述符关得太早，后续读取失效；同一文件并发打开触发两次扫描；最后一个句柄关闭时挂载标记被移除；扫描期间文件被改名，裁决落到错误节点；超时后返回权限错误而不是明确的拒绝原因；嵌套挂载递归标记失效；可执行文件打开事件没处理；已删除文件的事件仍去读路径；进程号复用时把裁决记到新进程；裁决服务重启后旧标记全丢；同一进程先打开后执行，两个事件各扫一次，第二个扫描期间文件已被替换。终端有上万台，策略不能依赖用户点确认，误放行比误拦更严重，安全运营还要求每次拒绝都能追到文件节点和扫描批次。队列溢出必须失败关闭，新访问以 FANOTIFY_QUEUE_OVERFLOW 拒绝，不能默认放行；同一文件节点的并发打开只能扫描一次并广播同一裁决；裁决必须绑定文件节点和生成号，改名期间不能把结果套到另一个文件；裁决服务重启要重建标记，重启前挂起的请求必须给明确拒绝，不能让进程永久阻塞。复盘会上有人问，为什么同一批样本在另一台机器上被拦住了。

## 运行方式
```bash
python -m pytest tests -q
```

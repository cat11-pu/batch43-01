# GSB Bugfix Task
## 题面
HTTP/3 灰度集群的 5xx 一直涨，抓包发现负载均衡器和后端对 QPACK 动态表的容量理解不一致，头部解出来全是乱码。编码器按自己的容量插入表项，解码器按另一份配置驱逐，索引整体错位；动态表插入和驱逐没有同步，正在被引用的表项被删掉；阻塞流的数量没有上限，一个慢流把整条连接卡死；同名同值的重复插入没有去重，表很快被撑满；Huffman 解码接受非法填充位，头部值被解成别的字符串；头部字段大小限制只在编码端生效，解码端照收；流被复位后动态表里的引用没有释放；收到 GOAWAY 还把新流往里塞；并发流引用了已驱逐的索引，解码器直接崩溃；服务端推送也去改动态表，客户端状态对不上；容量设成零仍然接受插入；网关重启后动态表清空，但对端还以为旧表有效。前端同学说关掉压缩就能绕开，但生产不能一直关着；网关和后端又是两套团队维护，配置各改各的。值班说再放量就得回滚。容量不一致必须报 QPACK_ENCODER_STREAM_ERROR 并关闭连接；阻塞流超过对端声明上限时必须回 QPACK_DECOMPRESSION_FAILED；表项只有在所有引用释放后才能驱逐；重启后必须把容量置零并通知对端重置动态表。先把回退开关确认清楚，别再放量。

```bash
python -m pytest tests -q
```

# GSB Bugfix Task
## 题面
全盘加密的解锁服务接入了可信平台模块，最近一批机器改过安全启动策略后还能用旧策略解封，安全基线直接判了不合规。运维试着把失败机器重启，有时能解封有时不能，现场完全靠运气；安全基线要求每次解封都记录用了哪组寄存器、哪个策略会话。密封模块会把平台配置寄存器组在两种哈希算法之间选错；策略会话随机数复用；先解封再读寄存器，读数已经变了；字典攻击锁定计数不生效；空授权也能解封；安全启动策略变了旧会话仍有效；并发解封耗尽模块瞬态槽位；模块重启清会话，服务还拿着旧句柄；签名策略的过期时间不检查；解封过程中寄存器被扩展，读到的值不一致；失败后回退到无策略解封；多块磁盘共用一个策略会话，第一块解完后第二块拿到失效句柄。这批机器分布在三个机房，不能逐台重灌，服务重启时还得自己恢复，运维还要求解锁失败时能区分策略不匹配和硬件通信失败。寄存器不匹配必须以 TPM_PCR_MISMATCH 失败且不能释放密钥，禁止回退到无策略路径；策略会话只能使用一次，重放必须报 TPM_POLICY_REPLAY；模块复位或重启后缓存的会话句柄必须失效，首次解封要重建策略；并发解封必须串行，拿不到会话的请求返回 TPM_BUSY。模块厂商说瞬态槽位本来就少，并发一高必须排队。

## 运行方式
```bash
python -m pytest tests -q
```

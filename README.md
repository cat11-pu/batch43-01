# GSB Bugfix Task
## 题面
集团上了共享信号框架做连续访问控制，最近一次演练里，攻击者把截获的撤销事件重放，反而把无辜会话踢下了线，而真正被盗的会话还活着。值班在复盘里发现，撤销事件和登录事件走的是两条队列，先后顺序完全看运气；安全部要求事件账本能按主体回放最近十分钟的状态变化。信令服务不拒绝重复的事件编号；编号记录只在内存，重启就清空；签发方和配置的发送方不一致也接受；一个事件里多个事件类型只处理第一个；未知会话的撤销事件不落墓碑，后续同编号会话直接放行；事件乱序时撤销先到、建立后到，会话又活过来；验签用错密钥集；不检查过期时间，旧事件能撤销新会话；重复事件让撤销计数翻倍；发现文档缓存过期不刷新；事件里的主体和会话主体只比用户名不比签发方；并发处理同一主体的多个事件，最后写入的覆盖了更严格的撤销状态。这套东西接的是全集团的单点登录，演练已经暴露了状态竞态，不能等到真事件再修，也不能因为一条坏事件把正常会话全踢掉。重放事件必须报 SET_REPLAY 且不改状态，事件账本要跨重启保留；未知会话的撤销事件要写带过期时间的墓碑，窗口内同编号会话一律拒绝；乱序时已撤销的会话不能被后到的建立事件复活；事件里出现未知类型必须整条拒绝，不能只应用其中一部分。现在只能靠人工比对日志，安全部催得很紧。

## 运行方式
```bash
python -m pytest tests -q
```

# GSB Bugfix Task
## 题面
园区的智能电表通过 CoAP 加 OSCORE 往云端报表，最近运维发现同一块表重启后会连续丢好几分钟数据，抓包显示网关把新请求当成重放扔了。电表没有本地日志，出了问题只能靠网关记录还原。网关把发送方序号只放在内存里，重启归零，接收端把后续请求全部判重；部分随机数生成时复用了旧值，密钥流撞车；观察通知没绑定原请求的令牌，换一个观察者也能收到同一块表的读数；分块传输只按内容格式拼装，不同块大小的数据混在一起；重放窗口固定成三十二位，远超协议允许范围；安全选项的类型位没解析，外层码点被改写后仍能通过；组播请求没配组密钥也拿单播密钥去解；请求超时后仍然消耗序号，重启前后出现断层；令牌长度为零和九都放行；同一端点并发两个分块上传，组装缓冲互相覆盖；收到复位消息后观察关系没释放，通知还在继续发；网关和云端时间偏差大时，新鲜度校验把正常包判过期。现场有几千块表，换固件要走审批，网关必须兼容旧表的重传和乱序，云端看到的是数据缺口，现场看到的是表还在发。同一发送方加部分随机数的重复请求必须返回 4.01 且不能再次执行业务；序号要落盘，重启后下一跳用保存值加一，旧序号一律拒绝；分块组装要以端点、令牌和内容格式为键，键不一致时返回 4.08；观察取消或收到复位后必须释放注册，不能再发通知。这套网关的单测现在没有一条能过。


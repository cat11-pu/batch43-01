# GSB Bugfix Task
## 题面
数据中心东西向流量抖了三天，抓包发现两台虚拟化主机上的 VNI 对不上，同一个业务网段被塞进了两个隧道。注册表接受 VNI 零和全一，两个都当成合法业务；两台 VTEP 配了同一个 IP，后者把前者的 MAC 表覆盖；VNI 删除后组播组没有退出，流量还在往空隧道发；内层 MAC 学习没有按 VNI 隔离，跨业务互相污染；封装后没扣五十字节开销，大包全被丢；源端口哈希固定成一个值，交换机链路极化；远端 VTEP 地址来回跳，表项一分钟变几次；ARP 抑制缓存不随 VNI 删除失效，旧映射一直回；封装报文的保留位没检查也转发；VNI 创建和删除并发，留下半套表项；重启后转发表全丢，恢复瞬间整网泛洪；同一 MAC 在两个 VNI 下只保留一条。虚拟化平台有八百多个租户网段，隧道表一乱，排查只能靠抓包，业务方已经在群里催了。先把重复的隧道清掉。VNI 零和全一必须拒绝并报 VXLAN_VNI_INVALID；同一 VNI 加 MAC 只能有一条学习结果，且不能跨 VNI 复用；重启后要恢复远端 VTEP 和转发表，恢复完成前不得泛洪；VNI 删除必须原子清掉转发表和组播成员关系。业务方要求今晚之前给出根因。

## 运行方式
```bash
python -m pytest tests -q
```

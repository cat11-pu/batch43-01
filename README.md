# GSB Bugfix Task
## 题面
宽带装维反馈，同一个光猫重启几次就能拿到好几个 IPv6 前缀，后台看地址池掉得飞快，部分用户续租时还提示前缀不可用。装维师傅一个人管几个小区，没法逐台光猫去看租约，只能靠后台把分配结果说清楚。前缀代理同一设备标识重启后重复分配，租约库根本没查；中继换一个链路地址就能把别人的前缀重新绑定走；首选和有效生存时间不递减，过期前缀还在下发；一条请求里多个前缀只应用第一个，其余静默丢掉；前缀池碎片不回收，跑几天就耗尽；中继转发跳数不检查，形成环路；释放请求重复提交每次扣一次池子；快速提交和普通四步交互同时走，分配出两份；设备标识的两种格式大小写、分隔符没归一；续租和释放并发，留下孤儿租约；前缀长度四十八和七十二都收；服务重启后空闲位图从零重建，已经租出的前缀被再次分出去。地市有十几万台光猫，地址池一乱就是批量投诉，装维现场只能重启光猫，越重启拿到的前缀越多，财务按前缀数结算。同一设备标识加接口标识并发申请只能分配一个前缀，第二个响应要带回同一个绑定且不能再扣池子；释放之后再续租必须返回 NoBinding；服务重启后要恢复租约表，已分配前缀不能重复下发，过期回收只能在有效生存时间之后；前缀长度不在四十八到六十四之间必须抛 InvalidPrefixLength。后台那套单测至今没有一条能跑通。

## 修复要点（`dhcpv6_pd_broker.py`）

- 绑定键为归一化 DUID（小写十六进制、去除 `:` `-` `.` 分隔符）加 IAID；中继链路地址仅记录，不参与绑定身份，换链路不会抢占或复制前缀。
- 同一 DUID/IAID 的重复请求（含快速提交与四步交互、并发请求）直接返回既有绑定，不重复扣池；所有公共方法由同一把锁串行化，续租与释放并发不会产生孤儿租约。
- 生存时间按绝对到期时刻存储，续租返回剩余的首选/有效生存时间并随时间递减；只有超过有效生存时间才回收，期间地址池满时返回 `NoPrefixAvailable`。
- 一次请求的多个前缀整体分配，容量不足时原子失败，不产生半分配；释放后前缀回到池中可被重新分配。
- 重复释放与释放后续租均返回 `NoBinding`，且重复释放不会再次扣减地址池。
- 租约表以 JSON 原子落盘（临时文件 + `os.replace`），重启后重建已分配集合，已租出前缀不会再次下发。
- 前缀长度仅接受 48–64（越界抛 `InvalidPrefixLength`）；中继跳数超过 `max_hops` 抛 `HopLimitExceeded`。
